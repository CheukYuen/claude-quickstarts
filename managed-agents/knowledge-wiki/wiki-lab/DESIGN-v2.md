# wiki-lab 设计 v2：以记录为底座的投研底账

状态：设计稿，未实现。日期：2026-10-21。本稿取代 [DESIGN.md](DESIGN.md) 中 P2 及以后的安排；原稿不改，P0 准备和 P1 小样按原稿完成，结果见 [P1 交付记录](runs/p1-20261021/REPORT.md)。本稿不以 invest-lab 现有的角色、契约和写入规则为前提（第 2 节）。第 15 节记录抽取调用方式的决定。

![wiki-lab v2 架构：原件经抽取和代码核验成为记录，代码组装出研究底账并生成页面，研究 agent 经查询接口读取并回写；缺口经独立的取数阶段补数，新资料走同一条线增量，问答评测决定去留](assets/architecture-v2.svg)

## 1. 为什么改

目标变了。原稿要回答"wiki 这种形态能不能用于 AI 投研"，由人读页面来判断。后续目标是自动化完成公司和行业的 AI 投研分析：wiki 的主要使用者变成研究 agent，人读的是同一份内容生成的页面。

P1 的做法是模型写叙述页面、代码查结构、人工抽查原文。在新目标下，它暴露了四个结构问题：

| 问题 | P1 里的表现 | 根因 |
| --- | --- | --- |
| 知识写在叙述文字里 | 口径和性质只能写成限定句，俊知时间线约 1,900 字里有 9 处"不能／不以／不代表"；缺口是嵌在 Markdown 里的 JSON 代码块；机器无法查询、计算、比对 | 没有记录层：口径、性质、金额组成没有字段可放，只能写进文字 |
| 核验只到结构 | [checks.py](checks.py) 只验页码存在；内容正确靠 25 条人工回读；价格表列数错位、页面上不显示成表格，也没被拦下 | "引用支持论断"没有变成可由代码检查的条件 |
| 用多轮工具会话做一次性任务 | 8 块抽取用了约 627 万输入 token，原文 40.5 万字，约每字 15 个 token，其中约 92% 是缓存命中；2 次 900 秒超时；整编和补缺另用约 649 万 | 抽取本质是"原文进、记录出"，不需要工具循环 |
| 按模板产出，不按问题产出 | 俊知 3 份公告共 16 页，撑出 6 个公司页；长飞缺口 36 条，研究问题和一元差异、名称变体混在一起；三个缺口页约占阅读页文字的 41%；补缺读了 15 页原文，实际补上 0 项 | 页面和缺口没有挂到研究问题上 |

## 2. 总体思路

模型只负责从原文抽出带字段的记录；核验、计算、组装和生成页面交给代码；模型再在核验过的记录上写综合判断和研究结论。wiki 是建在记录上、按公司和行业组织的研究底账，Markdown 页面是它生成的阅读视图。

原稿的原则基本不变：每条事实带页码和披露日；主体合并要有原文依据；实绩、指引、机构预测和判断分开；截点按披露日；wiki 不替作者下结论。变的是这些原则落在哪里：从 prompt 里的文字约束和页面上的限定句，改成记录字段和代码校验。

**与 invest-lab 的关系。** 本稿不受 invest-lab 现有规则约束，不沿用它的角色分工（M、D-抄录、D-判断等）、证据契约和写入规则；invest-lab 本身也有问题，要另行优化。两边共用 invest-sources 资料库和取数模块（5.2 节），另外只约定两个接口：研究 agent 通过第 3 节的查询接口读 wiki，研究结束后按第 11 节回写。invest-lab 优化时可以直接读这套记录，不再单独抽取，但那是 invest-lab 的改造，不是本稿的前提。

## 3. 分层

| 层 | 内容 | 谁写 | 怎么保证对 |
| --- | --- | --- | --- |
| L0 原件 | PDF、逐页文字、数据商返回文件、资料清单 | invest-sources 资料库；wiki-lab 的取数阶段只追加写入，建库时只读 | 清单版本链与哈希（[corpus.py](corpus.py) 已实现） |
| L1 记录 | 五类带字段的记录；从原文抽取的带逐字摘录和定位，Choice 转换的带字段名和报告期 | 抽取器；Choice 返回由代码转换 | 代码核验（第 7 节） |
| L2 研究底账 | 主体登记表、时间线、指标序列、计算指标、口径认定、缺口、上一轮判断 | 代码组装；模型只写综合判断 | 每句引用记录编号；计算数附公式和输入记录编号 |
| L3 研究 | 研究结果（交接包、驱动、报告） | 研究 agent | 读 L2；研究结束后把判断、口径和教训写回 L2 |

阅读页面由 L1/L2 生成，可以随时重建，不手改。研究 agent 通过查询接口读，不读页面：

| 接口 | 返回 |
| --- | --- |
| `records(主体, 指标, 期间, 截点)` | 截点前已披露的记录，含覆盖关系 |
| `timeline(主体, 截点)` | 事件序列及当时所处阶段 |
| `derived(主体, 指标, 期间, 截点)` | 计算指标、公式和输入记录 |
| `gaps(主体或问题)` | 缺口、类型、已查范围 |
| `page(来源, 页)` | 冻结的逐页文字 |

## 4. 记录（L1）

### 4.1 五类记录

| 类型 | 例子 | 关键字段 |
| --- | --- | --- |
| 指标数值 | 长飞 2026H1 营业收入 9,808,962,180 元 | 主体、指标、期间、单位和币种、合并范围、性质、数值 |
| 事件 | 2026-09-24 青海目标公司股权转移登记完成 | 主体、事件类型、发生日、阶段 |
| 条款与义务 | 过户后六个月内须启动三期生产，未按期开产则卖方可没收 15 百万元履约保证金 | 义务方、内容、期限、起算事件、条件、金额组成 |
| 主体关系 | 青海中利更名为青海俊知，并成为江苏俊知的全资附属公司 | 主体、关系、起止日（未知为 null 并说明） |
| 陈述 | 管理层对增长原因的说明；美银的盈利预测；长飞转引的 CRU 需求预测 | 陈述方、性质（判断、指引、机构预测、转引）、原始出处 |

所有记录共有的字段：记录编号、来源和定位（PDF 页序、表或章节）、逐字摘录、披露日、基准日（`as_of`）、是否市场内容、抽取版本。

### 4.2 记录格式由 wiki-lab 自定

记录格式由 wiki-lab 自己定义和演进，不受 invest-sources `shared-evidence/1.0` 契约约束。字段设计参考其中在研究轮里用过的部分：数值与逐字摘录、定义（指标、单位、币种、期间、主体、范围）、性质、出处（直接或转引、共同出处）、定位、限制和覆盖关系。长飞中报已有 8 条这样的记录（`evidence/601869.SH-20260822-interim-2026h1/extracts/v1.json`），可作对照样例。

在此基础上：

- 五类记录各有自己的字段（4.1 节）。
- 每条记录有对象键（主体、指标、期间），供查询、覆盖判断和增量使用。
- 金额组成和可加性用字段表达。例如偿付支持所涉债务记为 `components: [本金, 利息, 罚息, 违约利息]`、`as_of: 2026-06-30`，页面渲染时自动标注"基准日合计，含利息"，不再写限定句。

同一个抽取器有两种模式：建库时按必抽清单全量抽取（覆盖模式）；研究 agent 需要某项而底账里没有时，按请求定向抽取（请求模式）。

存放：记录放在 wiki-lab 自己的仓库里，随 wiki 一起版本化，每条记录带核验状态（第 7 节）。

### 4.3 必抽清单

每种文档类型一份清单，写明哪些项目必须有记录，或明确标"本文档无"。先写两份：

- **A 股中报、年报**：主要会计数据与财务指标、分部信息、非经常性损益明细、收入与成本构成、现金流主要项目、借款与债券、担保、关联交易、承诺及或有事项、期后事项、分红方案、产能与在建工程、管理层对增长原因的说明、风险因素。
- **港股交易公告**：交易阶段与日期、对价及组成、付款安排与状态、其他义务（偿付支持、保证金）、条件与期限、标的财务摘要、估值基准、交易各方及股权链、上市规则分类。

研报的清单（机构预测表、转引出处、评级和目标价归入市场内容）在 S1 阶段补齐。

## 5. 历史财务数据源

### 5.1 A 股报表科目直接用 Choice，查值只作报警

A 股完整报表（`ctr`）的原表科目直接用 Choice 的值，不逐值回原文定位对数。只取 `ReportType=1`（合并报表，即当期最初公布的数）；`ReportType=2`（合并报表(调整)）是后来重述过的数，不用。披露日取返回里的 `FIRSTNOTICEDATE`。Choice 派生的字段不在此列（5.3 节）。不使用 Wind 作第二家数据商。

依据（2026-10-21 本机只读核对，未调用接口）：

- **覆盖**：`vendor/choice/choice-20261004-yofc-financials-market.json` 是长飞 6 期完整三表，资产负债表 151 个字段、利润表 73 个、现金流量表 125 个。Wind 的长飞回执在清单备注里写明是摘要或定向字段，如"非完整利润表""不等于逐科目完整表"。
- **抄录准确**：2026H1、2025、2024 三期共 444 个整数值，435 个在对应中报、年报的逐页文字里原样出现。没找到的 9 个都是 Choice 自行合计的科目（ACCOUNTBILLREC、ACCOUNTBILLPAY、OTHERPAY、OTHERCINCOME），例如应收票据及应收账款 7,896,300,353 = 应收票据 626,305,410 + 应收账款 7,269,994,943。也就是说，原表科目的 435 个值没有一个抄错。
- **重述和截点**：现有文件全部按 `ReportType=1` 取数，返回的报表类型都是"合并报表"。6 期的 `FIRSTNOTICEDATE` 依次是 2026-08-22、2026-03-28、2025-03-29、2024-03-29、2023-04-01、2022-03-26，和清单里对应定期报告的披露日一致。

**查值报警。** 每次读入新的 Choice 返回，代码按证券代码和 `FIRSTNOTICEDATE` 找到对应的定期报告，检查每个原表科目的值是否出现在它的逐页文字里，做法同上面的"抄录准确"核对。找不到、又不是派生字段的值进人工队列，记录照常生成，核验状态标"待复核"。对应报告不在资料库里时记"未查值"，不阻塞。这项检查用来发现抄录错误、更正公告和口径变化；它不定位报表页、科目行和期间列，也不给记录记页码。

**出处。** Choice 转换来的记录没有逐字摘录和 PDF 页序，是 4.1 节共有字段的例外：出处写 Choice 返回文件的资料编号、字段名和报告期。需要看原文时，由查询接口按数值到对应报告里搜页。

**适用范围。** 本节只适用于 A 股 `ctr` 的原表科目。港股标准化字段（`css`）、分部和附注、Choice 派生字段不直接用（5.3–5.5 节）。现有证据只来自长飞一家公司的一般企业三表；金融类公司用的是另一套报表，接入前先跑一次查值。

### 5.2 取数和建库分开

wiki-lab 自带一个独立的取数阶段，负责调用 Choice；建库阶段仍只读冻结、带哈希的文件。分开以后，同一批输入重跑得到同一批记录，结果可复现；接口失败、重试和授权问题只影响取数，不会让一次构建半途而废。

**取数阶段**

- 输入是缺口生成的取数请求（requests.json，第 9 节）。只按缺口取，不预先全量拉取；每轮有调用预算。
- 调用 Choice，保存原样返回、查询参数、取数时间和 SHA-256；资料登记只追加，不改旧记录。取不到的按缺口记下原因，同一请求不反复重试。
- A 股完整报表一律用 `ReportType=1`（5.1 节）。
- 取回的文件写进共用的 invest-sources 资料库，沿用现有清单格式，不在 wiki-lab 里另存一份。
- 接口调用复用 invest-lab `.agents/skills/choice-quantapi-skill` 里的代码，抽成两边共用的取数模块，不再写一套。
- 目前只接 Choice。公告、研报等原件的下载，以后可以按同样方式接入。

取回的文件作为新一批输入走增量（第 10 节）。

**建库阶段**需要补的三步：

1. **读入**：[corpus.py](corpus.py) 目前完全不读 `vendor/`，需要加上按公司和报告期选取 Choice 返回文件，并像 PDF 一样绑定清单行和哈希。清单里 192 条数据商记录的 `published_date` 全部为 null，截点改用返回里的 `FIRSTNOTICEDATE`（5.1 节），例如 2026H1 数据为 2026-08-22。A 股报表只读入 `ReportType=1` 的返回。
2. **转换**：按字段对照表（5.3 节），把 A 股完整报表（`ctr`）和港股标准化字段（`css`）转成 L1 记录。
3. **查值**：按 5.1 节在对应报告的逐页文字里查每个原表科目的值；找不到的进人工队列，不记页码。

**上线前要处理的**

- Choice 的登录凭据和调用额度在 wiki-lab 里管理。
- 港股完整报表接口和汇率查询先由取数阶段单独测一次（5.5、5.6 节）。
- invest-sources 现在写明资料清单只由 D-抄录写入。取数阶段要往里写，需要改这条规则，或者把共用取数模块定为资料库唯一的写入者，由 wiki-lab 和 invest-lab 共同调用。

### 5.3 字段对照表

每个 Choice 字段都标明是"原表科目"还是"Choice 派生"。派生字段（如 5.1 节的四个合计科目、港股的 TOTALREVENUE）不作为披露事实使用；需要时用原表科目由计算层算出。

### 5.4 分部和附注从原文抽

Choice 和 Wind 的分部口径不同，而且都没有分部成本和利润。Choice 的长飞光传输分部收入 6,502,458,446 元含分部间收入（对外 6,125,485,258 + 分部间 376,973,188），Wind 的 61.2549 亿元是对外收入。分部利润、非经常性损益明细、担保、债务到期、产能等内容，不论用哪家数据商，都要从原文抽。

### 5.5 港股和覆盖缺口

- **俊知**：现有 Choice 数据只有 `css` 标准化字段。`b1` 批次是 41 个财务字段；`b2` 批次是主营构成，清单备注称只有 Rank=1，收入和毛利不全。
  - 对照 2025 年报，`b1` 的 36 个非空数值里约八成能在原文找到，其余是 Choice 的自定口径。例如 TOTALREVENUE 2,646,988 千元 = 年报"收入"2,638,523 + "其他收入"8,465，不等于年报的收入；OPERPROFIT、WCCHG 等原表里没有。
  - `b2` 的主营构成文本有乱码（如"阻燃软电电系列""光光系列"），不能直接使用。
  - 港股完整报表接口在现有记录里没试过，需要先由取数阶段测一次。测通之前，俊知的历史财务按"原文抽取 + 逐字核验"处理。
- **四家同行**（亨通、中天、烽火、长芯博创）：Choice 文件只有有息负债、市值、估值倍数等零散字段，没有三表。原稿只纳入同行的管理层讨论章节；是否需要同行三表由研究问题清单决定，按需生成取数请求、由取数阶段取回，不在建库时预先全取。

### 5.6 适用范围

本节只管历史财务。港币汇率和香港无风险利率目前用 Wind，因为 Choice 三次汇率查询都返回空（`vendor/choice/choice-20261015-bc-fx-*`）；如果也要去掉 Wind，需要另找中债或官方发布的来源。行情、估值倍数等市场内容不在本稿范围内。

## 6. 抽取

- **按文档结构切块**：中报、年报按标准章节和附注编号切，公告按整份，研报按章节或整份。不再按 10 万字定长切，以免表格被切到两块里（P1 长飞有几条缺口就来自跨块续表）。
- **每块一次模型调用**：输入是章节的逐页文字、必抽清单和记录格式；输出是 JSON 记录和覆盖清单，覆盖清单对每个必抽项写"已抽"或"本文档无"并附页码。不需要工具循环：仍用 `codex exec`，原文放进 prompt，只读沙箱，用 `--output-schema` 约束输出（第 15 节）。
- **多轮 agent 会话**只留给需要探索的环节：有歧义的主体判断、缺口检索、研究本身。
- [P1 抽取 prompt](prompts/extract.md) 里的规则保留，包括区分交易阶段、金额组成分开记录、预测不改成实绩、转引注明共同出处，改由记录字段和第 7 节的校验来承载。

## 7. 核验

| 检查 | 方法 | 不通过时 |
| --- | --- | --- |
| 摘录存在 | 逐字摘录在所引页的冻结文字里出现（空白规范化后比较） | 拒收该记录 |
| 数值在摘录中 | 数值按单位规则格式化后出现在摘录里 | 拒收该记录 |
| 字段合法 | 单位、币种、期间、性质、关系类型的取值合法；未知日期为 null 并有说明 | 拒收该记录 |
| Choice 查值 | A 股原表科目的值出现在对应报告的逐页文字里（5.1 节），不定位页码 | 进人工队列，记录标"待复核" |
| 必抽覆盖 | 每个必抽项都有记录或"本文档无" | 补抽该章节 |
| 记录间一致 | 同键记录数值冲突、合计不等于分项、分部合计不等于集团 | 进人工队列 |
| 页面渲染 | Markdown 表格列数一致、链接可达、页面只引用存在的记录 | 渲染失败 |

"摘录存在""数值在摘录中"只适用于从原文抽取的记录；Choice 转换来的记录没有摘录，走"Choice 查值"。

人工只抽查代码验证不了的部分：主体是否同一家、性质分类是否正确、有没有漏抽重要内容。抽查结果记入记录的核验状态。

## 8. 研究底账（L2）

### 8.1 研究问题清单

公司和行业各一份问题清单，按投研分析的需要定义。每个问题写明需要哪些记录。

| 公司（示例） | 行业（示例） |
| --- | --- |
| 业务构成与各业务的驱动因素 | 产品与计量单位 |
| 盈利拆解：经营利润和一次性收益各占多少 | 价格序列：来源、口径、能否拼接 |
| 毛利率能否持续：量、价、结构 | 需求池及预测出处 |
| 现金流质量：经营现金流与利润、营运资金 | 产能台账：宣布、名义、有效 |
| 资产负债与表外义务：债务到期、担保、承诺 | 参与者的位置，以及到公司页的链接 |
| 资本开支与产能：名义产能、在产产能、实际产量 | |
| 重大交易：阶段、对价、其他义务、期限 | |
| 管理层指引与机构预期 | |

只为有材料的问题生成页面；没有材料的问题只出现在缺口里。

### 8.2 计算层

毛利率、扣非占比、对价加其他义务的合计、期限届满日、价格变动倍数等，由代码按公式计算，结果记下公式、输入记录编号和"计算"标记。模型不做算术，也不回避算术。

### 8.3 时点视图

每条记录都有披露日和基准日，任意截点的视图就是一次过滤：只取截点前披露的记录，同键多条时取最新披露的那条，被覆盖的旧值仍保留。原稿 5.1 节说的"按历史截点重建以后再设计"，在记录层上不需要单独设计。

市场内容用记录上的标记表示，看价前视图按标记过滤，不再靠 `market/` 目录隔离。P1 的市场页就是因为单独放在目录里，没有任何页面链接到它。

### 8.4 主体登记表

主体用只追加、不改动的登记表管理，规则同来源编号注册表。代码先按股票代码、统一社会信用代码、中英文全称生成同一性候选，模型只判断有歧义的候选对，同一性依据记在关系记录上。取消 P1 的"至多 16 个核心实体"上限。

### 8.5 阅读页面

页面由代码按模板从记录生成，模型只补综合判断段落。规则：

- 概览页先写结论：关键数字（换算成易读单位，如亿元）和一两句判断，每条带引用。
- 引用直接链接到冻结的逐页文字，用相对路径。
- 运行编号、阶段名等流程信息不进正文，放在页脚或运行记录里。
- 一个对象只开有内容的页；材料少的对象（如一笔交易）合成一页。
- 限定条件由字段渲染成固定格式的标注，不写成否定句。

## 9. 缺口

缺口不再由抽取器逐块自由提出，而是"重要问题缺的记录"：问题清单里某个问题需要的记录不存在或没通过核验，就生成一条缺口，按问题权重排序。抽取瑕疵（一元差异、列位、名称写法差异）进质检队列，不算研究缺口。

缺口按处理方式分四类：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 库内可解 | 另一章节或另一份已收资料有答案 | 自动检索记录和逐页文字 |
| 库外公开可得 | 公司另一份公告、同行三表 | 生成取数请求（requests.json）；Choice 数据由取数阶段执行（5.2 节） |
| 不公开 | 交易合同、民事调解书、评估报告 | 标"公开渠道不可得"并停查，有新资料时重开 |
| 质检 | 列位、合计差、名称变体 | 进质检队列，不进研究页面 |

状态仍用原稿的三种：已解决、资料里没有、没查完。"资料里没有"仍须写明查过的原文页。

## 10. 增量

- 新资料按第 6、7 节抽取和核验，得到新记录。
- 每个页面和计算指标都记下自己依赖的记录键。新记录按（主体、指标、期间）找到受影响的页面和计算，只重算这些。
- 同键记录按披露日判断覆盖关系，旧记录保留。例如 S48 的"400 吨"被 S50 的"400 吨/年"更新。
- 原稿第 8 节的名字、层级标签、链接三条线找候选的方法作为补充，用于新记录还没挂上主体或问题的情况。
- `changes.md` 由代码按记录的增减和覆盖关系生成，人只看结论变化。

## 11. 研究轮回写

研究 agent 读 L2，产出研究结果（交接包、驱动、报告）。研究结束后，把口径认定、研究判断（依据、反证、失效条件，每条都引用记录编号）、缺口的已查范围和教训写回 L2。判断依赖的记录一旦被覆盖或修正，代码就把这条判断标为"待复核"。

## 12. 评估

从 P2 起，不再以"读页面判断格式"作为门槛，改用问答评测：

- **题集**：原稿第 9 节的查看清单，加上长飞首轮研究关注的关键问题，共 30–50 题，每题带标准答案和原文页码。
- **比较三种底座**：直接读原文、P1 wiki、新记录层。
- **指标**：答对率、引用正确率、成本、耗时。
- codex-spike 的原文问答基线可以复用。

## 15. 抽取调用方式（2026-10-21 已定）

**决定**：继续用 `codex exec`，不改为直接调用模型 API。抽取改为单轮调用：块的逐页文字、必抽清单和记录格式经标准输入放进 prompt，用 `--sandbox read-only`，用 `--output-schema` 把最后一条消息约束成记录 JSON，prompt 要求不执行命令。整编、补缺等多轮环节沿用现有 runner 和工作区门禁。

**为什么不换 API。** 本稿初稿据"约每字 15 个输入 token"估计，改 API 能把输入 token 降一个数量级。按 P1 的用量拆开看，这个估计站不住：

| P1 抽取 8 块，各取成功的一次 | token |
| --- | ---: |
| 输入合计 | 6,270,366 |
| 其中缓存命中 | 5,738,112 |
| 未缓存输入 | 532,254 |
| 输出（含推理 52,216） | 218,709 |

- 未缓存输入约 53 万，和 8 块原文约 40.5 万字是同一量级，说明每块原文只按全价读了一次。单次调用也要读一遍原文，这部分省不掉。
- 能省掉的是 574 万缓存命中。它来自工具循环：每执行一条命令，上下文就重读一次，大块执行了 18–26 条命令。按 API 计价，缓存命中的单价远低于未缓存输入，所以 token 数降一个数量级不等于成本降一个数量级。
- 输出 token 与调用方式无关。改为 JSON 记录后，输出可能更多。
- 本机 `codex` 用 ChatGPT 账号登录，不按 token 计费；改 API 反而要按 token 计费。
- 工具循环在 `codex exec` 里就能去掉，不需要换调用方式。

S2 实测单轮调用的输入、缓存、输出 token、命令数和耗时，和上表对照。模型仍执行命令，或单块输出太长被截断的，在 S2 记录下来，并相应调整 prompt 或切块。
