# wiki-lab 设计：在 1300.HK 全量资料上做 knowledge-wiki 实验

状态：设计稿，未实现。日期：2026-10-21。

![wiki-lab 架构：构建、增量、查询与对照、用量整编四条流程共享一个按版本保存的 wiki](assets/architecture.svg)

## 1. 要回答的问题

[codex-spike](../codex-spike/) 用 4 份文件、约 4.9 万字符跑通了 knowledge-wiki 的机制，但规模太小：wiki 比原文还大，原文对照几乎打平，说明不了 wiki 有没有用。

wiki-lab 把语料换成俊知（1300.HK）的全量资料，约 487 万字符，是 spike 的约 100 倍。它要回答四个问题：

1. **实体页**：有更名依据的青海中利 / 青海俊知能否合为同一实体，中利集团等不同主体能否通过股权和交易关系连接，时间线上的空白能否形成问题？
2. **开放问题逐项处置**：每题能否留下有依据的处置或暂缓原因？新资料进来后，缺失问题和受影响的旧答案能否被重新检查？
3. **查询与原文对照**：在这个规模上，读 wiki 比搜原文省多少 token，答案好多少？
4. **用量整编**：拿查询记录再整编一次，后续提问的读取成本会不会下降？

**不在范围内**：不改 invest-lab 和 invest-sources；不用 Managed Agents 和 Dreaming；不用向量库；第一版不做自动评分。本实验只验证 wiki 的检索、实体关联、缺口处置和增量能力，不验证 invest-lab 的研究判断和交接流程。

## 2. 和 codex-spike 的区别

| 项目 | codex-spike | wiki-lab |
| --- | --- | --- |
| 语料 | 4 份，18 页，约 4.9 万字符 | 37 份，1,643 页，约 487 万字符 |
| 抽取单位 | 一份文件一个会话 | 按页切块，每块约 10 万字符，一块一个会话 |
| 实体 | 整编时顺手建 4 页，没有固定格式 | 抽取时记"提到的主体"，整编时建实体页；固定 frontmatter，程序校验 |
| 开放问题 | 一行一个，补缺只挑 5 题 | 每题有稳定 ID；每版恰好一条有效处置，允许笔记未找到或注明原因的暂缓 |
| 增量 | 不支持 | 只抽新文件，冻结旧编号与块，重查缺失及受新证据影响的旧处置 |
| 查询 | 4 道题写死在代码里 | `ask.py` 随时提问；初次构建不见题目 / 答案，用量整编仅见 train-wiki 日志，test / gold 不提供 |
| 用量整编 | 没有 | 只用 train-wiki 查询记录，在同一语料的独立分支上产出新版本 |

运行方式和 spike 一样：Python 负责编排，每个阶段启动一个新的 `codex exec` 会话，模型通过 Codex 的工具读写文件。

### 3.2 编号与截点

- 默认完整选择的 A 批首次按披露日期分配 `S01`…`S36` 后，冻结 `source_id → 短编号` 注册表；子集校准沿用这些编号。B 批即使是较早披露的历史资料，也只追加为 `S37`，不重排旧编号。日期另作排序字段。`_sources.json` 保存稳定 source_id、短编号、原件和逐页文字哈希；同 ID 重复登记须核对身份一致，不能凭最后一条静默覆盖冲突。其他 cutoff / exclude 的独立实验按实际来源数建表，不强行补足这些编号。
- 引用格式沿用 spike：`[S12 p34]`，页码是 PDF 页序。新增原件修订不能覆写已绑定字节；本实验的增量用例仅追加一份新来源，不扩展为原件修订管理系统。
- 截点参数 `--cutoff`，默认 2026-10-15（俊知研究轮的截点）。披露日晚于截点的文件不进语料，无法核实披露日的条目记录限制并排除。要回答"某天之前知道什么"，就用那个截点另建并冻结 wiki 和配对原文语料；不让后披露资料进入该题的任何一组。

### 3.3 切块

- 按页切，不拆页。一块最多约 10 万字符；超过一页的单页（极少见）单独成块。
- 小公告合并：同一类型、披露日相邻的小文件（例如 9 份月报表，每份 10 页约 1 万字符）合成一块，但每页仍保留各自的 `[SOURCE: Sxx]` 和 `[PAGE: N]` 标记。
- 单来源块编号如 `S05.c03`；多来源合块使用独立编号如 `C001`。`chunks.json` 明确记录每块包含的 source_id、短编号、页码及文本哈希；不能把合块内容都归给其中一份来源。块编号和成员在首次生成后冻结，增量不重新拼接或切分 A 批，笔记和问题只写自己的文件。
- 估计约 50–60 块。招股书单份约占 28% 的字符；如果第一阶段测出成本太高，它是第一个可以推迟的文件（`--exclude`）。

### 3.4 分两批放入：先不放 002309

002309.SZ 的 `2025-098` 公告披露：2025-12-12 董事会批准转让青海中利 100% 股权并同意签署协议，协议约定受让方为青海青银、股权价款为 951,461.90 元。公告仍使用“本次交易完成后”，没有报告实际签约或交割完成日。2026 年俊知公告能证明当时青海青银已持有标的，但不能补出确切取得日。核对入口为 invest-sources 中 `002309.SZ-20251215-announcement-2025-098` 的 PDF 第 1、4 页。

这份资料在俊知研究中是后期才补入的。本实验只模拟“后补相关历史资料”这一情形：

- **A 批**：1300.HK 的 36 份选定文档，不等同于当时研究的输入清单。
- **B 批**：增量加入 002309 一份，检验增量流程能否把它连上。

### 3.5 首次提取保留什么

同类任务复用固定提取约定，每次只替换来源、块内容和输出位置；以下要求写入计划中的 `extract.md`，不把具体评估题或答案放进去：

- 数字连同主体、指标定义、单位、币种、期间、合并范围、实际 / 指引 / 预测 / 推断性质一起保留。
- 对影响用法的关键原话保留短摘录，包括付款与投产期限、起算点、退款 / 没收条件、偿债支持义务和本金 / 利息组成。背景可以归纳，不能把这些条件压成一个总数。
- 表格保留表头、行列对应、负号和相关脚注。遇到跨块续表或缺少定义，记录待回查页码，不自行补足前文。
- 每块笔记附简短覆盖说明：已读页码、重要表格 / 条款是否覆盖、未提取或不可读内容的位置及原因。问题只记真实疑问，不为达到预计题数凑题。
- 每个开放问题标 `priority`：影响主体身份、交易阶段、金额口径或时间线的标 `high`，其余标 `normal`；并在 `recheck_pages` 里写下最可能有答案的原文页。只有 `high` 题在补缺时可以回查原文（第 7.2 节）。
- P1 人工对照原文抽查上述内容；哈希、页数或文件存在不证明语义完整。新增要求仍使用来源笔记，不另建生产证据层。

## 4. 流水线

| 阶段 | 程序做什么 | 模型做什么 | 产出 |
| --- | --- | --- | --- |
| 0 准备 | 读清单、按截点筛选、核对哈希、复制逐页文字、冻结来源与块编号 | 无 | `corpus/`、`corpus-manifest.json`、`chunks.json` |
| 1 抽取 ×N | 每块一个工作目录，只放这一块原文；并发启动；检查产物格式 | 读原文，写笔记、提到的主体、开放问题 | `sources/`、`mentions/`、`open_questions/` |
| 2 合并 A-v0 | 原样拷到一起；把所有"提到的主体"汇成一张名字索引 | 无 | `wiki-A-v0/`、`_mentions_index.json` |
| 3 补缺 ×M | 按来源分批，每批约 40 题；统计回查页数；检查每题有一条当前有效处置 | 搜笔记；`high` 题在页数上限内定点回查 corpus；回答、记录未找到或暂缓 | `dispositions/<batch>.json` |
| 4a 整编：实体 | 复制成新版本；校验 frontmatter、别名唯一、链接可达 | 合并别名，建实体页，写关系和有效期 | `entities/*.md` |
| 4b 整编：视图 | 校验引用页码、来源笔记不变 | 写时间线、指标表、风险清单、索引；发现时间线空白就新增问题 | `timeline.md` 等，`open_questions/_gaps.json` |
| 4c 补缺与回流 | 只处理 4b 新增的问题，检查有效处置后再发布 | 同阶段 3；把处置反映到相关实体 / 视图 | 追加处置，更新相关页面，发布 `wiki-A-v2` |
| 5 查询 | 复制 wiki 到只读工作目录；记录读取过程和用量 | 先读索引，按需读页面，回答并写状态行 | `queries/<version>/wiki/<qid>/` |
| 5' 原文对照 | 同上，只换成该版绑定的 `corpus/` 和来源目录 | 搜索原文作答 | `queries/<version>/raw/<qid>/` |
| 6 用量整编 | 只汇总指定版本的 train-wiki 记录；复制冻结的 `wiki-A-v2`；检查改动范围 | 重排索引和交叉引用，标示有依据的推断，新问题留待后续 | `wiki-A-usage-v3`、`usage/changes.md` |
| 增量 | 冻结旧来源 / 块身份；只抽新块；按名字匹配列出受影响旧问题的候选 | 确认候选是否受影响；重查缺失与受影响的旧处置，再整编 | `wiki-AB-v3` |

每个阶段都在上一版的**副本**上工作，旧版本不动（沿用 spike 的 `wiki-v0`、`v1`、`v2` 做法）。

版本名带语料批次，`wiki-A-v2` 之后分成两个平行分支：

| 版本 | 来自 | 语料 | 用途 |
| --- | --- | --- | --- |
| `wiki-A-v0` → `wiki-A-v1` → `wiki-A-v2` | 首次构建 | A 批 | `wiki-A-v2` 冻结后是两个分支的共同起点 |
| `wiki-AB-v3` | `wiki-A-v2` + 增量 | A+B 批 | 只测新增 B 批（P3） |
| `wiki-A-usage-v3` | `wiki-A-v2` + 用量整编 | A 批 | 只测用量整编（P4） |

两个 v3 互不作为对方的输入。4c 只做一次有界回流；回流中再发现的问题登记为 `DEFERRED` 并写原因，不递归新增整编轮次。

## 5. Wiki 的格式

```text
wiki-<批次>-vN/
├── _index.md                 入口：哪类问题读哪些页
├── _sources.json             稳定短编号 ↔ source_id、哈希、日期、页数（程序写）
├── _mentions_index.json      所有"提到的主体"按名字汇总（程序写）
├── sources/S05/c03.md        逐块笔记（抽取写，之后任何阶段不得修改）
├── mentions/S05/c03.json     这一块里出现的主体名字和身份信息（抽取写）
├── open_questions/S05-c03.json   这一块的开放问题（抽取写）
├── open_questions/_gaps.json     时间线空白产生的问题（整编写）
├── dispositions/batch-07.json    稳定处置ID、版本、supersedes；保留历史（补缺写）
├── entities/<slug>.md        实体页（整编写）
├── timeline.md               事件时间线（整编写）
├── metrics.md                数字和口径（整编写）
├── escalations.md            冲突、缺口、需要取得的资料（整编写）
└── usage/changes.md          用量整编改了什么（用量整编写）
```

需要程序检查的部分（主体、问题、处置）用 JSON 或 frontmatter；给人读的部分用 markdown。

上例是单来源块；多来源合块按其独立块 ID 保存笔记、mentions 和问题，归属以 `chunks.json` 的页成员表为准。每版的 corpus-manifest 只列该版实际使用的来源子集；P0 盘点到 B 批，不代表 B 能进入 A 批的模型工作目录或原文对照。

## 6. 能力一：实体页

第 6、7 节示例里的 `[S31 p4]` 这类引用编号都是示意，实际编号由阶段 0 分配。

### 6.1 抽取时记录"提到的主体"

每块抽取除了笔记，还写一份 `mentions/<块>.json`。抽取者只记原文里出现的名字和身份信息，**不做合并判断**：

```json
[
  {"name": "Qinghai Zhongli Optical Fibre Technology Co., Ltd.",
   "name_zh": "青海中利光纤技术有限公司",
   "role": "收购标的", "identifiers": {},
   "facts": ["2013-07-05 成立"], "cite": "[S31 p4]"}
]
```

程序把所有 `mentions` 汇成 `_mentions_index.json`：同一个名字出现在哪些块、哪些页。这一步不调模型。

### 6.2 整编时建实体页

整编会话读名字索引和相关笔记，决定哪些名字是同一主体，每个主体写一页：

```markdown
---
name: qinghai-trigiant
canonical: 青海俊知光纤技术有限公司 / Qinghai Trigiant Optical Fibre Technology Co., Ltd.
type: company
aliases:
  - text: 青海中利光纤技术有限公司 / Qinghai Zhongli Optical Fibre Technology Co., Ltd.
    kind: former_name
    valid_to: 2026-09-24
    cite: "[S33 p1]"
identifiers: []
relations:
  - {rel: subsidiary_of, target: trigiant-group, valid_from: 2026-09-24, cite: "[S33 p1]"}
candidate_links: []
---
- 2013-07-05 成立，生产光纤预制棒、光纤 [S31 p4]
- 一期、二期在产年产能 400 吨，三期 600 吨待投产 [S33 p2]
```

规则：

- **同一性必须有原文依据**：例如公告写明"更名为"。只有名字相似、没有依据的，放进 `candidate_links` 并写理由，不合并。把两个主体误合成一个，比不合并更危险。
- **关系带有效期**：`valid_from` / `valid_to`。股权换手、更名都保留历史。未知生效 / 交割日期写 null 并说明，不能用董事会批准日、协议日或披露日代替；有证据的事件日期和披露日期分别记录。
- **程序检查**：frontmatter 能解析；同一个别名不能出现在两个实体上（出现就记冲突）；`[[链接]]` 和 `target` 都指向存在的页；每条事实都有引用，且页码存在。

### 6.3 时间线空白自动变成问题

整编写 `timeline.md` 时，同一主体两个状态之间缺了一段（例如"2013 年设立"和"2026-09 青海青银持有 100%"之间，没有任何股权变动记录），就在 `open_questions/_gaps.json` 里新增问题。阶段 4c 处理后更新相关页面，再发布；若未找到答案，保留限定范围的未知或暂缓，不把时间线空白自动当成漏披露。

## 7. 能力二：开放问题逐项处置

### 7.1 问题和处置的格式

```json
{"id": "OQ-S32c01-003",
 "question": "卖方青海青银取得标的的协议股权价款是多少？",
 "raised_by": "S32.c01", "cite": "[S32 p4]",
 "entities": ["qinghai-qingyin", "qinghai-trigiant"],
 "priority": "high", "recheck_pages": ["S32 p4"]}
```

```json
{"id": "OQ-S32c01-003",
 "status": "NOT_FOUND_IN_NOTES",
 "answer": null, "cite": [],
 "checked": "全部来源笔记、名字索引；搜索 青银 / Qingyin / 中利 / transfer",
 "needed": "先定点回查 A 批原文；若仍未见，再列卖方取得标的的交易文件或前股东出售公告",
 "disposition_id": "D-A-007-003", "version": "wiki-A-v1",
 "supersedes": null, "batch": "batch-07"}
```

| 状态 | 必填 |
| --- | --- |
| `RESOLVED` | 答案，至少一个引用 |
| `CONFLICT` | 冲突双方各自的引用，未决原因 |
| `MISSING_IN_CORPUS` | 回查过的原文来源 / 页码 / 检索范围、仍缺内容及需要什么文件；结论只限当前选定范围 |
| `NOT_FOUND_IN_NOTES` | 笔记检索范围、未找到什么、建议回查的原文位置；不声称原文没有 |
| `DEFERRED` | 本轮未完成检查或暂缓的原因、尚需检查什么 |
| `NOT_RELEVANT` | 理由 |
| `DUPLICATE_OF` | 指向的问题 ID |

问题应在首次生成时拆成原子题，例如把历史出售方、协议价款、批准日期、实际完成日期分开；不要用一个 `RESOLVED` 掩盖未答子项。补缺时才发现复合题的，本轮保留原 ID，标 `DEFERRED` 并记录建议拆分，不删除或重编号。所有问题有记录，不代表所有问题已查完或已回答。

### 7.2 分批处理全部问题

- 题数仅作预算粗估，不要求每块产出 5–8 题；真实问题可能少于预计的 300–400 个。程序按来源分批，每批约 40 题，一批一个会话，可以并发。
- 先在 wiki 里用 `rg` 搜索，再读相关笔记。只有 `priority: high` 的题在笔记里找不到答案时才回查原文：先查问题的 `recheck_pages` 和来源笔记覆盖说明里的待回查页码，再按名字在当前版本 `corpus/` 里用 `rg` 定位。
- 每批回查设页数上限，初始默认 60 页，P1 时校准。程序从工具调用记录统计实际读过的原文页，超限写进运行报告；超出上限仍未查完的题标 `DEFERRED`。回查过的来源和页码写进 `checked`。
- 不能从笔记未找到直接跳到 `MISSING_IN_CORPUS`：`normal` 题和未回查的 `high` 题最多标 `NOT_FOUND_IN_NOTES`。
- 每批只写自己的 `dispositions/batch-NN.json`，不改其他文件。
- **程序检查**：每个问题在当前版本恰好有一条有效处置；历史处置保留但不重复计为当前状态。检查稳定处置 ID、`supersedes` 指向、各状态必填字段及引用页码。缺记录不算结构完成；`DEFERRED` / `NOT_FOUND_IN_NOTES` 可以发布，但必须单列数量、原因和影响，不能计为研究已解决。

### 7.3 新资料进来时重查旧问题

增量只追加来源和块，不修改旧来源笔记。重查分两类：

- **未答的旧问题全部重新排队**：所有 `MISSING_IN_CORPUS`、`NOT_FOUND_IN_NOTES`、`DEFERRED`。
- **可能受影响的已答问题，程序出候选、模型确认**：程序用新块 `mentions` 里的名字，按字符串匹配实体页的规范名和别名，得到受影响的实体；问题的 `entities` 字段或当前处置的引用涉及这些实体的 `RESOLVED`、`CONFLICT`，列为候选。指标、事件层面是否真受影响，由补缺会话逐题判断；判断为不受影响的，写一行理由。

候选规则、候选数和确认结果写进 `increment_screening.json`，便于检查漏筛。字符串匹配会漏掉新文件里第一次出现的名字，这类遗漏只能靠人工抽查发现。不能假定已解决问题永久有效。

旧处置不改；新处置带独立稳定 ID 和版本，`supersedes` 指向被替代的处置 ID。每个问题按当前版本的替代链确定唯一有效状态，历史记录不重复计数。重新整编实体与视图时使用这些当前有效处置。

## 8. 能力三：查询入口和原文对照

### 8.1 随时提问

```bash
python3.12 ask.py "青海收购的对价和承接债务能否相加？" --wiki runs/<run>/wiki-AB-v3
```

```bash
python3.12 ask.py "同一个问题" --wiki runs/<run>/wiki-AB-v3 --baseline
```

- 每次提问开一个新只读会话。wiki 组放指定版本的副本；原文组只放与该版本绑定的 `corpus/` 及同一来源目录。两组的来源集合、哈希、截点、问题、模型配置、工具和回答要求相同；基线不能默认读取后续新增的 B 批。
- wiki 组先读 `_index.md`，原文组使用中性的搜索原文提示词，不要求读取不存在的 wiki 索引。两组都区分披露、预测和推断；未找到答案时说明已查范围和缺什么，不把检索失败自动等同于原文缺失。
- 回答最后一行是程序可读的状态：`STATUS: ANSWERED | PARTIAL | NOT_FOUND | NOT_IN_CORPUS`，以及 `MISSING: <缺什么>`。`NOT_IN_CORPUS` 需有相应原文检查依据或有效缺失处置；否则用 `NOT_FOUND`。
- 记录按 `queries/<wiki_version>/<arm>/<qid>/` 分开，arm 为 wiki 或 raw，防止同题不同版本互相覆盖。保存问题、版本、来源清单哈希、配置、读取文件和顺序、token、耗时、答案及状态；前后哈希确认输入未改。
- 不向会话提供其他问答、答案要点或无关目录。只读限制写入，不等于读取路径隔离；来源范围还需任务约束和工具读取轨迹审计，不能仅凭工作目录副本宣称完全隔离。

### 8.2 评估题：构建过程看不到

spike 没有把四道测试题传给构建阶段，但提取 / resolve 的关注点与题目高度重合，属于定向机制演示，不能据此证明未见题泛化。wiki-lab 明确分离构建输入、使用反馈和保留题：

- 评估题放在 `questions/eval.json`，**在第一次构建之前冻结**，包括 split、适用语料 / 版本、截点、答案要点、出处页码、允许表述与重要错误判据。A、A+B 的答案要点可不同；不能用 B 批答案评分 A 批。
- 不把题目和答案文件复制进构建 / 整编工作目录，不提供 test 或 raw 对照日志。检查实际传入 prompt 和可见读取轨迹；题目原文子串检查只是辅助，不能证明语义未泄漏。若发生暴露，注明该题不能充当保留题证据。
- 构建 prompt 只写通用的问题类型（主体、事件、金额口径、实际与预测、缺口），不写具体题目。

评估题按要测的失败场景设计，每类至少 2 题：

| 类别 | 例子（方向，不是最终题目） |
| --- | --- |
| 同一主体多个名字 | 青海中利和青海俊知是什么关系？ |
| 数字被后续文件取代 | 青海三期的产能状态在各次公告里怎么变化？ |
| 同名指标口径不同 | 公告里的负债和券商说的取得负债是同一口径吗？ |
| 必须跨多份文件 | 2023 私有化提出方和 2026 收购的买方是什么关系？ |
| 时点 | 截至本轮绑定的截点，交易进行到哪一步？（默认 2026-10-15，两组同截点；本轮不另加早期截点实验） |
| 陷阱：语料里没有 | 交割后青海三期的实际产量是多少？ |
| 单份文件直接查 | 2025 年报的分部收入是多少？ |

每题标 `split: train` 或 `split: test`。只有 train 题在 `wiki-A-v2` 上的 wiki 组查询记录能进入用量整编。test 在 `wiki-A-usage-v3` 冻结后，分别对 `wiki-A-v2`、`wiki-A-usage-v3` 和相同 A 批原文提问，所有 test 日志均不交整编者（见第 9 节）。第 10 节的定向验收题标 `split: acceptance`：不进入用量整编，也不计入 train / test 的泛化结论。

### 8.3 对照指标

wiki / 原文对照使用同题、同来源集合；用量整编另比较固定 A 批上的 `wiki-A-v2` / `wiki-A-usage-v3`。不要把两种对照或新增资料效果混为一个结果。

- 用量：输入 token（含缓存）、缓存 / 未缓存输入、输出、工具次数、读取文件数、耗时；计入失败与重试，构建、增量、用量整编成本分别列示。宿主未暴露项写 null，不由任务次数猜金额。
- 质量：按冻结的答案要点人工记录命中、遗漏、错误和拒答，打分表放在 `questions/scores.csv`。实体误并、捏造、关键金额 / 时间 / 口径错误及错误拒答单列为重要错误；语义抽查不能由页码存在检查替代。
- 第一版报告观察值和逐题差异；质量变差不能只因更快或更省而判为优化。压缩率是描述指标。小幅改善只有在少量代表题重复后仍出现，才能称为较稳定收益；不建设大型评测框架。

第一版不做自动评分。题目和打分规则稳定之后，再考虑加一个评分会话。

## 9. 能力四：用问答记录再整编

### 9.1 输入

P4 从冻结的 `wiki-A-v2` 复制产生 `wiki-A-usage-v3`，不从加入 B 批的 `wiki-AB-v3` 开始。两者绑定同一 corpus-manifest、来源与块哈希及截点。

`usage_digest.json` 只接收 P2 的 `split=train + arm=wiki + version=wiki-A-v2` 记录：问题、状态、读取文件及顺序、跳转、token、耗时、答案和 `MISSING` 内容。程序按元数据白名单筛选，排除 raw、test、gold / 答案要点、P3 或其他版本的记录。

### 9.2 允许和禁止的改动

| 允许 | 禁止 |
| --- | --- |
| 调整 `_index.md` 的路由，让常见问题一步找到页面 | 修改 `sources/` 下的任何笔记 |
| 在实体页之间补交叉引用，把常被一起读的事实放到一处（保留原引用） | 删除事实 |
| 记录有依据的查询推断，保留推导与原始引用并标"推断"，人工抽查其支持关系 | 把查询回答自动升级为已核事实或研究已接受判断 |
| 把未答问题登记为 `DEFERRED`，注明需后续检查 | 本轮自动新增来源、外部取证或再启动补缺循环 |

**程序检查**：来源 / 块注册表、manifest 和 `sources/` 哈希不变；新增引用页码存在；改动清单与差异一致。另人工检查关键事实与限定是否保留、推断是否被误写成事实。此阶段可以重排材料并显式化推断，收益应称为“使用反馈整编”效果，不能全部归因于索引重排。

### 9.3 怎么衡量

- P2：在冻结的 `wiki-A-v2` 上问全部 train 题及其 A 批原文对照，只保留 train 题的 wiki 组记录作为 P4 反馈输入。
- P4：用上述反馈生成 `wiki-A-usage-v3` 并冻结后，再问 train 题；test 则分别对 `wiki-A-v2`、`wiki-A-usage-v3` 及同一 A 批原文问一遍。全部使用新会话和同一配置；test 查询可以后置，关键是始终不把其日志交给整编。
- 比较两版的同题质量、缓存与未缓存用量、读取行为和耗时；分别报告 train 与 test，未见题也必须有旧版对照。原文对照可按相同配置复用已有记录，并注明采集时间及缓存差异。
- P3 的 B 批新增证据只用于独立的增量用例验收，不与 P2 / P4 的成本或质量差异合并归因。报告查询收益时同时列出一次性构建和用量整编开销。

## 11. 成本和时间

现在只能粗估，P1 会给出实测值。

- 会话数：抽取约 50–60 个，首次补缺约 10 个，实体 / 视图及有界回流另计；再加增量、用量整编和查询。查询按 train 与 test 各自的 `wiki-A-v2`、`wiki-A-usage-v3`、原文三组分列，不把旧的“约 20 题 × 2 组、约 100 会话”当作完整预算。
- spike 中 1–2 万字符文件的抽取观察约为 70–90 秒、约 8 万输入 token（含大量缓存）；只作参考。10 万字符块的实际开销由 P1 测，不沿用固定倍数假设。
- 全量抽取可用 P1 实测的每块用量 × 块数粗估，补缺、整编、增量、查询、失败重试分别加总。缓存和固定会话开销另列，不能只按字符比例推金额。若排除招股书，重新冻结该实验的来源清单和两组输入，不与完整语料结果混比。

## 12. 程序保证和模型负责

| 程序保证 | 依靠模型 |
| --- | --- |
| 原件哈希一致，只读不改 | 读懂原文，包括双栏排版混在一起的研报 |
| 独立输出位置、允许文件清单、写入差异检查；来源笔记冻结 | 抽取是否完整、关键定义和条件是否保留 |
| 旧版本 wiki 不被修改 | 判断哪些名字是同一主体 |
| 实体 frontmatter 格式、别名不重复、链接可达 | 关系和有效期是否正确 |
| 每题每版一条有效处置，替代链与必填字段齐全 | 处置结论及缺失判断是否正确 |
| 引用的来源和页码存在 | 引用的那一页是否真的支持这句话 |
| 查询工作目录前后不变 | 答案是否正确 |
| 显式输入白名单、digest 版本 / split / arm 检查、题文辅助扫描 | 是否存在语义泄漏、用量整编是否改善未见题 |
| 绑定两组相同来源 / 截点，以及两个 A 批版本相同的语料 | 质量是否退化、人工评分是否准确 |

程序检查只证明结构对，不证明内容对。内容要靠评估题和人工抽查原文。

本节列出的是计划中的控制，不是已实现保证；只读不等于读取隔离，格式和引用页码存在不等于事实已核实。实验产物不自动成为 invest-lab 已接收的证据或投资判断。
